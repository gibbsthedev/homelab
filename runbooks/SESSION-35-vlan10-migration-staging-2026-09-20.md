## 0. WHAT THIS SESSION WAS

Preparation for moving the Proxmox host and both VMs off the flat
`192.168.8.0/24` LAN and onto the routed `192.168.10.0/24` VLAN 10 segment
built in sessions 24-26.

## 1. WHY THE STAKES WENT UP

Earlier notes assumed the public-facing workloads still ran on AWS EC2. That
is no longer true — **all migration waves are complete and EC2 has no running
instances.** Everything, including `*.richgibbs.dev`, is served from VM101
on this Proxmox box.

So this is no longer a lab-only change. It takes the public sites offline for
the duration of the cutover.

**Why the sites survive an IP change at all:** `*.richgibbs.dev` is fronted by
**Cloudflare Tunnel**, which is an *outbound* connection from the VM to
Cloudflare. Cloudflare never dials in. The VM's LAN address is irrelevant to
it. The only thing that matters is how long the VM has **no working route and
no DNS**.

That reframes the whole risk: the danger isn't the address change, it's
anything that leaves a VM unable to resolve names or reach the internet.
Which is exactly what §2 found.

## 2. THE BIG FIND — DNS WOULD HAVE BROKEN BOTH VMs

Three layers each *claimed* to configure DNS on these VMs. Only the deepest
one was real.

### 2.1 What was staged, and why each would have failed

| Box | Staged setting | Why it fails |
|---|---|---|
| VM101 hermes | `dns=192.168.8.1;` | That's the Beryl's dnsmasq, which runs `localservice='1'` and answers **only directly-attached subnets**. A routed VLAN 10 host gets `Ignoring query from non-local network`. (Same finding as session 25, different victim.) |
| VM100 docker-agents | *no dns line at all* | It was DHCP; the DHCP client was writing `resolv.conf`. Going static means nothing writes it. |

### 2.2 The deeper problem — Tailscale owns `/etc/resolv.conf` on both

`/etc/resolv.conf` on both VMs is generated by Tailscale (MagicDNS) and marked
DO NOT EDIT. All queries go to `100.100.100.100` (tailscaled listening
locally), which forwards non-tailnet queries **upstream**.

That upstream was **`192.168.8.1` — the Beryl** — on both machines.

It only surfaced under:
```bash
sudo tailscale dns status
```
Unprivileged output just says *"Access denied: dns-osconfig dump access
denied"* — so a non-root check would have shown nothing wrong.

**Consequence:** the `dns-nameservers` and `dns=` lines are decoration. Worth
keeping as a backstop, but **Tailscale is the actual DNS authority.**

### 2.3 There are TWO separate tailnets

The detail most likely to confuse a future session.

| Tailnet | Auth | Suffix | Holds |
|---|---|---|---|
| `rgibbs21.rg@gmail.com` | Google | `tail523202.ts.net` | hermes (100.79.57.44) |
| `richgibbs-prog@github` | GitHub | `taila006d9.ts.net` | docker-agents (100.75.241.15) |

**A DNS change in one admin console does not affect the other VM.** Both had
to be changed separately.

Each tailnet also still lists a dead AWS node (`ip-172-31-85-166`, last seen
Jul/Aug) — worth deleting eventually.

### 2.4 The fix, applied to both tailnets

In each admin console → **DNS**:
1. Add a global nameserver (used Google Public DNS)
2. **Turn "Override DNS servers" ON** ← this step was initially skipped

Step 2 is not optional. With override **off**, a global nameserver is
*advisory* — the client keeps preferring the captured local value
(`192.168.8.1`). The tool says so itself:

> *"Tailscale may use this configuration if 'Override Local DNS' is disabled
> in the admin console, or if no resolvers are provided."*

Both conditions were true.

To force the client to re-fetch instead of waiting for its next poll:
```bash
sudo tailscale set --accept-dns=true
sudo tailscale dns status
```

### 2.5 Verified by function

Both boxes now return:
```bash
getent hosts github.com
140.82.114.3    github.com
```

`192.168.8.1` still appears under *System DNS configuration* on both. That is
now only a record of what the OS holds — it is no longer in the query path.

## 3. THREE MORE DEFECTS FOUND

### 3.1 `/etc/hosts` on Proxmox — would have broken the web UI

```
was:  192.168.8.2   pve-node1.local pve-node1
now:  192.168.10.2  pve-node1.local pve-node1
```

Proxmox resolves its own node name through this file, and `pveproxy` binds
based on it. Left stale, the node goes grey in the UI or the interface hangs —
symptoms that look nothing like a hosts-file problem.

> **This edit is LIVE immediately**, unlike the interfaces files. It is the
> only non-inert change made this session. Harmless in the gap before shutdown.

### 3.2 The `nico` typo — silently failing for months

The live Proxmox config had:
```
post-up /sbin/ethtool -K nico tso off    <- letter o, not zero
post-up /sbin/ethtool -K nic0 gso off
post-up /sbin/ethtool -K nic0 gro off
```

Line one has been erroring at **every boot**, so **TSO was never actually
disabled** — only GSO and GRO were. Corrected in the staged config.

Worth knowing *why* those lines exist: disabling offloads on a Realtek NIC is
the classic fix for corrupted transfers or stalls under load. If that was the
original reason, the fix has been running at two-thirds strength this whole
time.

### 3.3 Blog automation pointed at VM100's old address

`/home/ec2-user/blog/automation/runtime-config.json:15`
```
was:  "ssh_host": "ubuntu@192.168.8.10"
now:  "ssh_host": "ubuntu@192.168.10.10"
```

(A `.bak-20260912-fix` copy still holds the old value — not loaded.)

### 3.4 Stale resolver backups — left in place, flagged

`/etc/resolv.pre-tailscale-backup.conf` on **both** VMs contains
`nameserver 192.168.8.1`. Inert where it sits. Dangerous only if someone
restores it later without thinking.

### Correction to VM100's self-report — DO NOT TAG VLAN 10 IN PROXMOX

The VM recommended "ensuring Proxmox actually tags VLAN 10 on this VM's NIC."
**Do not do this.**

`gi2` is an **access** port — the switch places untagged frames into VLAN 10
itself. `vmbr0` is not VLAN-aware and the VM net devices carry no tag, which
is correct. Adding a tag in Proxmox would **double-tag into an access port**
and nothing would work.

The VM was guessing at an architecture it cannot see.
`show interfaces switchport gi2` already confirms the real one.

### Expected during step 6 — not a fault

`show ip route` currently shows **nothing** for `192.168.10.0/24`.

It should appear when Proxmox links up. **If it doesn't, that's the first real
signal something is wrong** — before any ping is even worth running.

## 11. THE LESSON FROM THIS SESSION

**A config line that is accepted without error is not the same as a config
line that takes effect.**

Every defect found tonight was that shape:

- `dns-nameservers` on VM100 — valid syntax, nothing reads it
- `dns=192.168.8.1` on VM101 — valid, but overridden by Tailscale
- A global nameserver in the Tailscale console — set, but *advisory* until
  override was enabled
- `ethtool -K nico` — failing silently at every boot for months

**None of these would have been visible after the cutover.** They'd have
presented as "containers can't pull images" and "the sites are down" while
ping worked fine — symptoms pointing nowhere near the actual cause.

The general defense is already in this project's lessons file, and it keeps
earning its place: **verify by function, not by configuration.**
